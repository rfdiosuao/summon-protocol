# SUMMON 硬件接入与演示准入标准

2026-09-22 · 项目准入标准 v1。资料核验不等于真机认证；本页没有把任何新硬件标成已通过实测。

## 1. 标准适用对象

准入对象是“设备 + 固件/驱动 + Shell Gateway + 网络 + 电源”完整组合，不单看芯片规格。设备可以直连网关，也可以通过 USB、串口、BLE 或厂商 SDK 桥接。Agent 仍运行在原电脑/服务器；设备不必装大模型、GPU、Linux，也不强制具备摄像头、麦克风、NFC 或可刷固件。

封闭固件只要有可复现的外部控制接口也可以接入。只有充电口、只能手动操作厂商 App、无法获得程序接口的设备，不作为主动执行壳。

角色分为：输入外设（摄像头/麦克风/读卡器）、执行壳（屏幕/音响/机械臂）、组合壳（多个外设由一个网关聚合）。被动 NFC 标签是寻址入口，不是联网设备或身份凭证。

## 2. 必须满足的八项条件

| 编号 | 硬性条件 | 可检查的证据 |
|---|---|---|
| H1 | 至少一项可编程输入或输出 | 官方示例或独立脚本能读取一帧数据、显示指定文字、播放声音或执行限定动作；操作步骤可复现 |
| H2 | 有可维护的适配入口 | SDK/API/协议或可编译固件；明确操作系统、板型、固件版本、安装方式；存在日志与恢复办法 |
| H3 | 设备链路与 Hub 链路同时可用 | 操作硬件期间网关仍能连接 Hub；SoftAP 设备必须验证双网卡/有线网络或按网络绑定的实际路由 |
| H4 | 稳定身份与授权 | 配对后绑定 device_id/shell_id；凭证由设备或受信网关持有；BLE 名字、地址前缀、NFC URL 只能用于发现，不能当认证 |
| H5 | 真实能力声明与结果回传 | 只声明已实现能力；区分“发出”“收到”“执行完成”；无证据报 UNKNOWN/FAILED，不能把网络 ACK 写成物理完成 |
| H6 | 可撤销、可去重、可拒绝旧指令 | 按现有契约校验 command_id、session_id、lease_epoch、expires_at；重复不重做，旧租约不执行；停止后清队列 |
| H7 | 断线、休眠和供电有确定行为 | 断线停止接收新任务，重连重新握手；不自动续做未知动作；供电可覆盖演示和连续验收；重启后身份不会错绑 |
| H8 | 可形成可追溯结果 | 记录设备型号/版本、能力、动作 ID、结果、时长、证据来源；经验上传可由网关完成，设备无需存全量历史 |

输入外设的 H5 是收到有效数据及时间戳，H6 是网关去重输入并停止采集/转发；不要求麦克风本身实现租约。执行壳的 H5/H6 必须落到实际设备控制路径。公网传输使用认证的 TLS；串口等本地链路可以由受信网关承担认证边界。

板侧 WSS 桥仍遵循 [ADAPTER](ADAPTER.md)：控制帧最大 16 KiB、每秒心跳、3 秒未收到网关心跳进入停止流程；物理设备的实际停止时间另测。USB/BLE 桥需映射同样的语义，不能假称现有仓库已经提供这些驱动。

## 3. 运动设备附加门槛

机械臂和外骨骼还必须有：正确供电与固定、型号对应的校准、位置/速度/力矩等本地限制、控制器反馈、现场停止手段，以及与公网和模型独立的控制看门狗。

远端 Agent 只发经过授权的高层任务；轨迹和电机闭环留在现场。心跳超时不是工业急停，不允许依赖云端网络实现运动保护。停止不得默认等于断电或回零：无制动关节可能下坠，必须按实际控制器验证。未知结果不得自动重试机械动作。

## 4. 演示准入验收

以下数字是团队新增的验收目标，不是厂商保证，也不是已有测试成绩。

| 测试 | 合格线 |
|---|---|
| 冷启动 | 连做 3 次，按固定步骤 60 秒内进入可用状态；不需重刷、反复删除配对 |
| 持续在线 | 30 分钟无不可恢复断线、崩溃、明显内存持续增长；测试期间使用真实外设 |
| 基本交互 | 20 次任务至少 19 次按预期完成；失败明确显示，不伪造成功 |
| 控制响应 | 排除模型推理/ASR/TTS，测网关发命令至设备接收，p95 ≤ 1 秒；动作完成按各能力单独设截止时间 |
| 交接 | 10 次 A→B→A 循环，旧壳停止后新壳才激活；零并发占用、零旧动作重放 |
| 异常 | 断网、拔数据线、设备重启各 3 次；结果可解释，重新授权后可恢复 |
| 协议拒绝 | 重复 ID、过期命令、旧租约各 3 次，全部正确拒绝或去重 |
| 经验记录 | 成功、失败、结果未知都能关联原动作；断网缓存有界，补传不重复；模拟和真机记录分开 |
| 运动保护 | 本地停止与失联保护全部通过；具体停止时间、负载和姿态写入记录，不能用 95% 成功率放行保护失败 |

状态统一使用：候选（资料具备）→适配中（实现未完成）→联调通过（单次闭环）→演示通过（以上验收完成）。模拟器单列，不作为硬件通过证据。

## 5. AI Passport 评估

结论：适合当前项目，是优先适配对象，但官方 main 不是已接入 SUMMON 的固件。

官方规格为 ESP32-C3、8 MB Flash、无 PSRAM，带屏幕、三个按键、麦克风和扬声器；具备 USB Serial/JTAG 调试路径。硬件基础能支撑显示和按键交互，推理放远端。

当前 main 的 Wi-Fi 示例只扫描、不连接；BLE 示例为不可连接广播。需要补充配网/有线桥、认证、命令收发、完成回执、停止和重连。带宽、无线稳定性及音频并发仍须实测。先完成 display.text + 按键输入，再加分块语音。不要一次引入大图、全双工音频和视频；必须记录空闲堆和最大连续空闲块。

NTAG213 是被动标签，两块 Passport 不能靠它互相读卡。用手机读取 URL 或另接 USB NFC 读卡器；不能因外壳有 NFC 就声明主动读卡能力。官方 demo/claude-buddy-port 可作为 BLE 适配参考，但不等于主分支已经具备它的能力。

若 Wi-Fi 联调受阻，可开发电脑 USB 串口桥作为有线演示路径；串口可调试不等于业务桥已实现。

来源：[规格](https://github.com/folotoy/ai-passport/blob/main/docs/hardware-design/specifications.zh_CN.md)、[官方仓库能力契约](https://github.com/folotoy/ai-passport)。

## 6. E06 / Luma 判断与调试止损线

用户提供的《唤名-附录-眼镜实测与接入现状》记录了 BLE 命令回复，说明并非所有层都完全不通；但没有本次独立复测。其 §9 明确标注 SSID 通知、RTSP 端到端、拍照和语音未验证，因此这些能力应标成“待验证”。

需要修正的推断：

- 上游验证的是 E09 / T1，用户设备是 E06 / S3；hw 2 和近似版本号不能证明全部兼容。
- 经典蓝牙活动与 BLE 失败相关，但记录也存在经典蓝牙已松开仍失败；“连接槽互斥”“必须删除配对”是待对照验证的假设。
- 地址前缀可缩小扫描候选，不能唯一认设备。结合 AA12 服务、握手信息和人工配对绑定；不要锁死 MAC。
- `0x67` ACK 只说明收到请求，不能证明 SoftAP 已就绪，更不能证明视频流已可用。

调试顺序：关闭可能抢占连接的手机 App/其他客户端 → 唤醒并扫描服务 → 连接 GATT → 订阅 AA14/AA15 → 对 AA13 带响应写入电量/版本查询 → 稳定重复读取 → 再单独测照片 → 最后测 Wi-Fi 视频。

先做 BLE 控制的最小复现，不把 Rust 编译、Wi-Fi 切网、音频播放混在一次测试里。上游 Python 示例仍依赖生成的 Rust 绑定；已有纯 Python 协议探针可用于排除编译问题，但要验证帧校验和解析。本文不自动修改配对、刷机或操作实物。

项目投入上限建议：先给 30 分钟验证稳定握手，再给 30 分钟取得一项实际输入；未达到就降为可选输入外设，不放进必经演示流程。后续可继续研究，不能把短时失败解释成硬件永久不兼容。

来源：[Luma README](https://github.com/metastable-lab/luma-core)、[接入指南](https://github.com/metastable-lab/luma-core/blob/main/docs/GUIDE.md)。

## 8. 手机和电脑

两者都能成为执行壳：通过专门的 Shell 客户端接收动作、显示内容/播放声音、返回完成证据。仅打开 operator 控制台不等于注册成设备。手机先做保持前台的 HTTPS 网页/PWA；权限和播放由用户手势开启，页面隐藏或系统挂起视为不可用，不保证后台常驻。

若要手机稳定桥接眼镜 BLE、设备热点和公网，应做原生 Android/iOS 适配并实测路由和后台行为；不要把浏览器硬件 API 视为跨平台统一能力。Web NFC 可优先评估 Android Chrome，其他平台用二维码或系统读取 HTTPS NDEF 标签，不依赖自定义 summon:// URL 有系统处理器。来源：[Chrome Web NFC](https://developer.chrome.com/docs/capabilities/nfc)。

电脑可以同时运行屏幕壳、USB/BLE 设备网关及 SDK，最适合做现场控制中枢。远端 Agent 与现场网关主动连接公网 Hub，无需给家中电脑开入站端口。首先验证现场网络能访问 Hub，再接外设。

## 9. 经验沉淀的边界

经验分两层：所有动作留下结果记录；从有证据的多次结果中提炼可复用经验。不能把一条执行日志、模型自述或传输 ACK 当成“技能已学会”。

经验记录建议包含：experience_id、关联 command/session、设备型号与固件/适配器版本、能力、任务条件、脱敏参数、结果、错误、耗时、证据来源、模拟/真机标识、可复用范围。以上是后续存储设计建议，不是对现有消息 Schema 的暗改。

网关负责采集与有界缓存，Hub 负责幂等保存和按权限检索，Agent 在相同能力/型号条件下参考历史。原始音频、视频和私人对话不默认进入共享经验。跨机械臂不能直接复用关节角或力矩；复用高层策略后仍执行本地校准与限制。机械完成和任务成功也要分开：关节到位不等于成功抓住物体。

建议主路径：远端 Agent → Hub → 现场电脑网关 → 两块 Passport；语音随后加入；机械臂在本地闭环与停止验收通过后加入。手机/电脑壳承担备用展示，眼镜作为可选感知增强。
