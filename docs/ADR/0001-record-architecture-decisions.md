# 0001. 用 ADR 记录架构决策

- 日期：2026-09-21
- 状态：Accepted
- 影响面：新增 `docs/ADR/`；`docs/FIRMWARE.md` 的变更纪律指向此处

## 背景

`docs/FIRMWARE.md` 的变更纪律写着"记录到 `docs/ADR/`，不静默扩字段"，
但 `docs/ADR/` 当时并不存在——文档里出现了一个死指引。

这个项目有一组会在压力下被反复质疑的决策：端口接口为什么只收回调、
为什么拒绝未知字段、为什么读卡器不挂机械臂。这些决策的理由分散在
`PROTOCOL.md` 与 `FIRMWARE.md` 的正文里，没有单独记录"当初为什么没选另一条路"。
赛期是 63 小时，Day3 还要冻结，届时没人有时间补写回忆录。

## 决策

建立 `docs/ADR/`，用编号只增不减的轻量格式记录影响协议、接口或安全模型的决策。

不要求所有改动都写 ADR——只有那种"三个月后有人问当初为什么这样"的才写。

## 为什么不是另一个方案

| 替代方案 | 否决理由 |
|---|---|
| GitHub Wiki | 是独立的 git 仓库，不在主仓内，`tools/validate_contract.py` 的链接检查覆盖不到；会和代码漂移，形成第二权威 |
| 只在 commit message 里写理由 | 检索困难，且 squash/merge 后会丢失讨论上下文 |
| 写一篇大的"设计原则"文档 | 原则会互相矛盾，且无法表达"这条后来被反转了" |
| 不记，靠口口相传 | 赛期三人已经会分工到不同模块；赛后开源后更无法口头传递 |

## 后果

换来：决策理由可检索；反转决策有地方记；新加入的人能看懂边界从何而来。

付出：每做一个架构决策多花约 15 分钟；需要有人记得写。

## 变更

无。
